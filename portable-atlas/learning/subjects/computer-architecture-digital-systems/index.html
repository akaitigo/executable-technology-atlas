03

配置の制約を読む

8-bit byte address

block  = address // line_bytes
offset = address % line_bytes
index  = block % line_count
tag    = block // line_count
line_count = capacity_bytes // line_bytes
hit = valid[index] and tag[index] == tag

本実装は2の冪geometryなのでshift/maskで計算。独立oracleは256B memoryのblockとslotを列挙し、同じformula関数を呼ばず照合する。

missとevictionは別

invalid行ならmissだがevictionなし。valid行の別tagならmissでresident blockを置換する。初めて読むblockの置換をすべて3C分類の「conflict miss」とは呼ばない。

今回の2blockは4行より少なく、他の3行が空のまま。再訪したblock0/4がmissする反例はcapacity不足ではなく指定indexの競合を示す。一般traceの3C自動分類は未実装。

05

答え：空きではなく、指定行を見る

address0はblock0、address16はblock4。両方index0、tagは0と1。line0で相手を追い出すため、正常traceは4 miss / 3 eviction。line1〜3は空のまま。

tagを省く意図異常版は1 miss / 3 hitだが、address16へbyte3を返してしまう。synthetic memoryの期待byteは19。誤ったhit率の改善を性能の改善とは呼べない。

同block内の別offsetを読むspatial inputではhitが増える。一方、line-sizeだけ変えると行数も変わる。比較条件を外して「大きいlineは常に良い」と一般化しない。

今回から実務判断へ

同容量・同trace・同cold startで比較し、hit率より先にdata correctnessを見る。指定indexの競合と総容量不足を区別できる。ただし実機の速さを決めるには構成とtimingの別証拠が必要。
