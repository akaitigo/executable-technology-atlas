前提と読む順番

revision、FIFO、操作順、観測起点が前提です。

  1. 元Cloud Subject：複製完了済みの仮定を確認。

  3. ack→未配送B read→配送後read→partition→復旧配送を比較。
  4. 関連WAL教材：read snapshotの起点と比較し、再現・実務判断、未教材へ。

初期A/B=revision0/value v0、router A。A writeはローカル更新＋enqueue後ack。deliver1回で先頭1件をBへ反映、partition中はqueue保持。routeは参照先選択だけ。freshはそのread stepのA revisionと一致するか。操作は入力順、観測は成功runの最後readです。

原典 → 実装 → 答え → 実務判断
AWS REL05-BP01を依存障害と縮退動作の設計観点として読みます。今回のreplicationは独自契約で、AWS製品の挙動を再現しません。
実際の辞書・FIFO操作・独立手書き表checker・raw保存runnerを比較。A ackだけではB revisionは増えません。B route availableでも未配送ならrevision0/fresh=false、配送後はrevision1/fresh=true。2更新中1配送ならB revision1、A revision2でfresh=falseです。
実務ではackの保証範囲、要求revision、readの観測step、配送完了を分けます。route切替をwriter昇格と同一視せず、読めたことからdurabilityやRTOを推論しません。
2in-memory store・単一writer・有限FIFO・逐次step。実cloud、quorum、consensus、durability、split brain、RTO保証、実性能、重複/逆順配送は未実証です。
