依存の完了待ちと、workerの空き待ち。4つの仕事の時刻を進め、同じ「待ち」の違いを読みます。

これはPythonで保存した仮想時刻の計算結果を読む画面です。操作で実workerを起動しません。図は保存値の説明で、実並列処理の計測画像ではありません。確認状態

1. 予想する

Aが終わるとBとC、両方が終わるとDへ進みます。通常の所要時間はA=1、B=4、C=2、D=1。単位は秒ではなくtickです。同時完了の対照だけB=2にします。

A → B / C → D DにはBとCの両方が必要

保存した計算結果を確認しています。

この条件の入力を読む


2. 時刻を進める
各時刻で終了した全件を処理してから、ID順に空き枠へ入れます。表示はその直後です。半開区間 [開始, 終了)なので、終了時刻には枠が空きます。


狭い画面では図と表を横にスクロールできます。タイムライン全体は保存済みの予定で、縦線がいま選んだ時刻です。

2. 入力を拒否した結果
payloadがnullなので、予定・仕事の状態・時刻は返していません。前に表示した予定は消しています。


3. 容量と依存を別に比べる
条件終了時刻開始時の依存違反
終了時刻4の故障は、終了時刻6の正常版より優れた予定ではありません。親が終わる前に始めているからです。同時終了の正常版の4は、Bの所要時間を変えた別条件です。


4. 原典と実装へ戻る
Python公式：done と get_ready は、呼出側が通知した完了に基づいて後続を解放します。APIが実workerの終了を検査するわけではありません。

5. 答え合わせと実務判断
枠を増やす前に、その待ちが依存によるものか容量によるものかを確認します。完了通知は、実際の仕事が終わった後に出す必要があります。全件が終わったという件数だけでは、依存を守った証拠になりません。
この有限模型は、最適なscheduler、実時間の高速化、公平性、失敗復旧、分散worker、外部副作用を保証しません。範囲と残る不足を確認してください。
