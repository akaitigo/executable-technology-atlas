# Atlas — 再試行できる失敗でも、今始めてよいか

失敗した、予算が残る、待ち時間が終わった、の3つは同じ判断ではありません。B→Dの小さな仕事で、再試行可能な合成失敗と再試行しない合成失敗を分け、失敗完了から2 tick待った境界と下流の状態を比較する教材です。実Airflow・実worker・外部要求を動かすものではありません。

## 前提から進む

[前提の要点](PREREQUISITES.md)で、DAGの依存成功、最初の失敗と最終失敗、再試行回数、容量と時刻の違いを確認します。既存の指数待機やdeadline（処理全体の締切）は再制作しません。業務処理を重複させないことが目的なら、同じ前提資料から既存のAPI再送教材へ戻ります。

この教材の新しい問いは、失敗の分類・再試行を追加開始する残予算・再開可能時刻を同時に満たすかです。Dのpending/blocked規則自体は既存のDAGで扱っています。[範囲](COVERAGE.md)と[原典との対応](SOURCE-MAP.md)で差分を確認できます。

## 予想する4条件

1. TRANSIENT（今回の方針で再試行可能）の後に成功するB。t=2でDはまだpendingか、最終blockedか。t=3にBを再開した時、残る追加回数はいくつか。
2. PERMANENT（今回の方針で再試行しない）の後に、入力表にはSUCCESSがあるB。予算2が残るからと次を実行してよいか。
3. TRANSIENTが3回続くB。初回を含む3試行の後に、さらに再開時刻を作ってよいか。
4. 最初の失敗でDを最終blockedに固定する故障。Bは後で成功しても、Dは実行されない。Bの回復だけで全体の成功と判断できるか。

[画面の入口](index.html)で2つの予想を選び、保存した計算を開きます。前後のボタンで時点を動かし、[固定契約](CONTRACT.md)・[原典との対応](SOURCE-MAP.md)・[計算の実装](model.py)を読んでから答えを表示します。[実装前の手表](hand-oracle.json)も別に固定されています。dueは失敗完了+2で、失敗開始+2ではありません。追加予算は待機を予定した時ではなく、追加試行を始めた時に減ります。実行可能な時刻に達したことを、実際の実行管理での即時開始保証へ広げません。

## 保存結果を確かめる手順

`python3 -B verify.py observations/calculation-20261006T223146682571Z` で、[保存結果の検査](verify.py)を実行できます。計算の実装は再実行しません。最初の[検査結果](observations/calculation-20261006T223146682571Z/verification.json)と計算時コードを保持し、現在の検査は[明示した履歴](observations/historical-source-map.json)を通じて対応を読みます。

実行はnice10の単一Python子、約0.206秒で終了・回収し、自動再試行0でした。[実行ログ](observations/calculation-20261006T223146682571Z/report.json)と、仮想時刻の0〜7 tickを混同しません。実時間で再試行を待った結果ではありません。新しい計算は、資源確認と他の作業との調整をしてから `run.py --record --gate …` で別の記録へ保存する設計です。

画面は `python3 -B serve.py --port 0` で表示できる静的ファイルです。表示されたローカルのポート番号へ接続します。この配信は計算せず、Markdown資料を文字として読むためのものです。今回の画面確認では、既存ページへ接続する担当が配信と資源を管理します。[画面確認の範囲](GUI-QA.md)を参照してください。
