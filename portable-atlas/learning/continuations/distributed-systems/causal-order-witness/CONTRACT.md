# Atlas：イベントの因果関係と表示順を分ける

この契約は実装前に固定する。現在の実行・画面・受入状態は `status.json` を正とし、この固定時点の説明を後から測定済みに書き換えない。

## 到達目標と前提

目標19「分散システム」の、イベント到達関係を独立に照合する段階に対応する。前提は状態遷移、グラフの経路、部分順序と全順序、同一メッセージの送受信である。既存の Lamport 型 counter と版の選択、Edge 教材の2成分 version vector と競合保持は前提であり、再制作・再加算しない。元学習経路 §6 実験1の、全イベント対の分類だけが今回の増分候補である。

利用者が学ぶ判断は「記録のどの情報を因果の辺にしてよいか」。因果関係は、この模型に明示したプロセス内の順序と送信→対応する受信、およびそれらの推移性から求める。画面の再生順は辺にならない。

## 固定入力

[inputs/events.json](inputs/events.json) に6イベントを固定する。

- P：a（m送信）→ b（ローカル処理）→ c（n受信）。
- Q：d（ローカル処理）→ e（m受信）→ f（n送信）。
- メッセージ：m は a→e、n は f→c。送受信の対応は完全な合成入力で与える。
- 固定時計：a=1, b=2, c=4, d=1, e=2, f=3。既存の計数規則を前提に手で付けたラベルであり、新しい時計アルゴリズムの測定ではない。
- 合法な再生順 R1=[a,b,d,e,f,c]、R2=[d,a,e,f,b,c]。プロセス内順序と送受信順序を両方満たす。
- 同じイベント同士は比較しない。異なるイベントの組は15組。a,b,c,d,e,f の字順は表の表示順にだけ使う。

## 4つの比較

1. **正しい辺・R1**：プロセス内の隣接辺4本と送受信辺2本から到達関係を求める。
2. **正しい辺・R2**：表示する再生順だけ変える。到達関係・時計ラベルは1と同じ。
3. **時計の大小を逆推論**：`C(x)<C(y)` を x→y と誤認する意図的な誤モデル。等値の場合はどちらも先としない。この条件では13組を因果と判定し、d→b と b→f が偽陽性になる。
4. **表示順を混入**：R1の隣り合う表示位置にも辺を加える意図的な誤モデル。15組すべてを因果と判定し、a→d, b→d, b→e, b→f の4組が偽陽性になる。

誤モデルは正常に計算終了する比較対象である。実行失敗とは区別する。再生順を変える比較は同じイベント集合の説明を変えるだけで、新しい実通信を発生させない。

## 実装前の手期待と独立確認

[expected.json](expected.json) と [HAND_TRACE.md](HAND_TRACE.md) に全15組を手で固定する。因果のある11組は a→{b,c,e,f}, b→c, d→{c,e,f}, e→{c,f}, f→c。並行4組は {a,d}, {b,d}, {b,e}, {b,f}。

各比較で15組の分類と偽陽性集合を照合し、正しい辺の経路も保存する。時計条件は11組すべてで成立するが、逆推論は2組で誤る。個数一致だけを受入にせず、組のID・向き・経路の各辺の出所を照合する。producer は expected を読まない。別担当は producer を読む前に独立の手表を確定する。

計算の採用は固定入力・コード・期待値のhash、完全なstdout/stderr、実行環境、終了・回収と別の検証器へ結ぶ。固定入力以外への一般的な検証器の正しさは主張しない。

## 原典と実装の対応

Lamport (1978), *Time, Clocks, and the Ordering of Events in a Distributed System* の刊行p.559「The Partial Ordering」の3条件を辺と到達関係へ、p.560「Clock Condition」を時計条件と逆推論の反例へ、pp.560–561「Ordering the Events Totally」を便宜的な全順序との違いへ対応させる。[著者公開PDF](https://lamport.azurewebsites.net/pubs/time-clocks.pdf) は今回の候補調査で本文を実読した。原典の図・本文全文は複製しない。

## 実行・表示・受入条件

Python標準ライブラリの小さい計算1回を予定する。追加install、実通信、SDK、設定変更は不要。rootの対象枠と独立した実行前確認、新しい資源観測の成立までは対象起動0とする。実nice>=10、対象CPU2秒・経過3秒、単一の所有子、有限kill/waitによる回収を計画し、自動再試行しない。具体的な資源guardは今回のroot方針と結び、古いbrowser PID許可を流用しない。不明な資源観測は実行可と扱わない。

画面は保存結果だけを読む。条件・予想→辺と経路・全15組の比較→原典/実装→答え→実務判断と限界の順にする。条件/予想/resetで古い結果と答えを消す。未実行・資料取得失敗と意図的な誤モデルを分ける。実DOM・1280/390の実viewport画像はrootの既存pageを使い、作者はbrowser/context/tab/serverを起動・終了しない。

限定Skillは保存状態から前提・公式規則・入力・実装・保存結果を辿る。Skill文書の存在、有限な読取利用、一般Agent評価は別に記録する。全体受入はCLI・実DOM/画像・資料導線・独立確認が揃うまでfalse。新規教材数への加算はrootの重複比較後の判断であり作者は0を維持する。

## 限界

「並行」はこの因果関係のどちら向きにも経路がない意味で、CPUで同時に走ったという測定ではない。同じ時計値は同じ物理時刻を意味しない。実ログの欠損、隠れた通信、外部の因果関係から辺を推定する問題は扱わない。この6イベント模型の成功を、全グラフ、一般の分散通信、causal consistency、linearizability、実時計同期、障害検出や業務上の正しさの保証へ広げない。
