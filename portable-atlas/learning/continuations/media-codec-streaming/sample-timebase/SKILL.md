# Atlas：丸めと時計の差を分けて説明する

`status.json` を最初に読み、保存した計算、実画面確認、最終独立受入を区別する。通常は `index.html` と保存した計算結果を読む。新しいプロセス、ブラウザー、音声デバイス、サーバーをこの Skill だけで起動しない。

前提として、サンプル位置 N は0始まりの境界、48,000 sample/s では N/48ms、原点0、整数msへの丸めは非負half-up（ちょうど0.5を上へ）と説明する。到着時刻やPCMのバイト数とは分ける。

1. 「1024サンプルずつ足すと、なぜ300区間でずれるか」には `thirds-three` と `thirds-long` を比較する。正確な1区間64/3ms、丸めた21ms、末尾6400ms対6300msを保存値から示す。絶対位置からの換算にも各境界の丸めがあり、常に誤差0とは言わない。
2. 「丸めるといつも早くなるか」には `below-half`、`half-twice`、`above-half` を使う。23サンプルの負誤差と0.5境界の正誤差を示し、24×2では絶対1ms対加算2msになることを確認する。Python roundの偶数丸めと同じ規約だと説明しない。`empty` は境界0だけとする。
3. 「絶対位置から計算すれば、時計のずれも直るか」には `fast-clock` を使う。名目6400ms、仮定の基準時間64000000/10001ms、時計差6400/10001msを示す。区間丸め−100msとの和を別に読み、誤差の相殺を時計補正の成功とは呼ばない。

予想→保存計算の操作→途中境界と末尾の比較→RFC3550§5.1と整数実装/Fraction検査→答え→実務上の限界の順に案内する。元の契約と手表を参照し、規約や保存値が不一致なら表示を拒否する。条件・予想の変更、欠落・改変・別条件の拒否では古い結果や答えを使わない。

実デバイスの時計・音質・実再生・RTP/RTCP準拠を尋ねられたら、この教材は測定していないことを明示する。+100ppmは仮定値、原点0と丸め方は教材規約で、RFCの要求ではない。新しい測定や補正方式は別の条件・許可・証拠が必要になる。3案内の確認を、あらゆるメディア問題への能力保証とはしない。

画面の案内では [Atlas の画面確認記録](GUI-QA.md) を参照し、実際に確認した条件と残る制限を伝える。過去の計算結果を、新たに計測した結果として扱わない。
