# Atlas：サンプル時刻の換算で生まれる二つのずれ

[学習画面を開く](index.html)。48,000 sample/s の固定計算から、丸め方による誤差と、時計の速さの差を分けて読みます。実デバイスの時計や音質を測った教材ではありません。幅1280/390の実画面操作・実DOM・画像保存を実施しました。確認範囲は [画面確認](GUI-QA.md) にあります。

## 前提と、最初の予想

1秒に48,000サンプルなら、48サンプルは1msです。サンプル位置 N は先頭から進んだ個数を示す境界で、原点を N=0、時刻0msとします。PCMのバイト数やネットワークで届いた時刻とは別です。

1024サンプルの1区間は、正確には64/3ms、約21.333msです。整数msへ丸めた21msを300回足す方法と、合計307200サンプルを最後に換算する方法は、同じ時刻になるでしょうか。

この教材は非負の値を最も近い整数msへ丸め、ちょうど0.5なら上へ丸めます。Python の `round` と同じ規約だとは扱いません。

## 操作して比べる

条件を選び、末尾の結果を予想してから保存計算を開きます。「前の境界」「次の境界」とスライダーで途中の位置へ移動できます。代表的な境界の表と、丸め誤差・時計差の線を見比べてください。

| 条件 | 名目の正確な末尾時刻 | 絶対位置から換算 | 区間ごとの丸め加算 |
|---|---:|---:|---:|
| 空 | 0ms | 0ms | 0ms。境界0だけ |
| 23サンプル | 23/48ms | 0ms | 0ms |
| 24サンプル×2 | 1ms | 1ms | 2ms |
| 25サンプル | 25/48ms | 1ms | 1ms |
| 48サンプル×3 | 3ms | 3ms | 3ms |
| 1024サンプル×3 | 64ms | 64ms | 63ms |
| 1024サンプル×300 | 6400ms | 6400ms | 6300ms |

空は「0区間・境界0だけ」で、架空の区間を計算しません。23サンプルでは負の丸め誤差、24サンプルの0.5境界では正の丸め誤差になります。累積誤差がいつも負になるわけではありません。

## 時計のずれを別に考える

最後の条件だけ、サンプル時計が名目より100ppm速いと仮定します。ppmは100万分の1で、100ppmは0.01%です。基準時計は理想、最初の時刻差は0、速さの差は一定とします。

同じ307200サンプルが進む基準時間 R は64000000/10001ms、約6399.360064msです。名目換算6400msとの差は約+0.639936ms。一方、区間の丸め加算の誤差は−100msです。合計は約−99.360064msであり、時計差と丸めが相殺して見えても、補正が成功したとは言えません。

絶対位置からの換算による丸め誤差 A−t は、各境界で0.5ms以内です。基準時計に対する A−R は、そこへ時計差が加わるため別の値です。この二つを同じ誤差として扱わないことが今回の判断です。

## 原典と実装を読む

[RFC3550 §5.1](https://www.rfc-editor.org/rfc/rfc3550#section-5.1) はサンプル時点と時計の周波数を説明します。今回の原点0・整数ms・丸め方・+100ppmは独自の比較条件で、RFCの要求ではありません。[原典と既存教材の対応](SOURCE-MAP.md) から、PCM・サンプル・提示時刻・到着時刻の既存経路へ戻れます。



[実装前の契約](CONTRACT.md) と [29点の手表](hand-oracle.json) を固定してから実装しました。[計算の実装](model.py) は整数の商と余りで丸め、[別の検査](verify.py) は Fraction と最近傍の比較で全618境界を照合します。計算機の浮動小数の誤差を時計差として扱わず、正確な分数を保存しています。
