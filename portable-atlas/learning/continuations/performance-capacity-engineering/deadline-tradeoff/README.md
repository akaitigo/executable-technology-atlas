# Atlas：平均待ちが最小でも、全員の締切を守れる？

[index.html](index.html) を直接ブラウザーで開く、3仕事の有限教材です。外部ライブラリ、通信、サーバー起動、インストールは不要です。前単元の平均と個人の完了から、**平均待ちと期限達成を別々に判断する**学習へ進みます。

模型の計算結果と、幅1280px・390pxのブラウザー操作を確認しました。6順序の比較表と13時点の表示が手計算に一致し、保存した7枚の実画面も目視確認しています。実CPU性能や、締切が早い順（EDF）の一般的な最適性を検証した教材ではありません。

## 到達目標

- 平均待ち、個別の完了時刻、期限違反を別の指標として説明する。
- FIFO、短い順、締切が早い順を同じ入力で比較する。
- 完了時刻が締切と同じなら間に合う、という規約を時間図で確認する。
- 手書き時間列と、処理時間を足す模型を別方式で照合する。
- 平均の改善だけで配分を選ばず、誰の期限を守るか確認する。
- 有限6順序の結果と、一般的な保証や実測性能を区別する。

## 1. 予想する

全仕事が時刻0に到着します。1台で1件ずつ処理し、途中では中断しません。切替費用は0、処理時間は正確に分かる仮定です。

|仕事|処理時間|絶対締切|
|---|---:|---:|
|A|4|6|
|B|2|3|
|C|1|7|

tickは架空の時間単位です。締切は「時刻6まで」のような絶対時刻。**完了時刻が締切と同じなら間に合う**とします。期限を過ぎた仕事も、比較のため最後まで処理します。別の処理へ送った要求の取消しや拒否を実装したものではありません。

FIFOは同時到着の登録順 A→B→C、短い順は C→B→A、締切が早い順は B→A→C です。平均待ちが最小になったら、全員の締切も守れるでしょうか。

## 2. 操作して比べる

1. 順序を選び、FIFOと比べた平均待ちと、全員の期限達成を予想します。
2. 「予想して比較を表示」を押します。未選択なら入力案内が出ます。
3. 時刻を0・1・2・3・6・7へ動かし、処理区間と締切の破線を読みます。
4. 最後まで処理した表で、完了・締切・超過を比べます。表はスライダー時点の完了分だけの平均ではありません。
5. 原典と実装を読んで、答え合わせを表示します。予想変更は結果・時刻・答えを消し、条件変更とリセットは予想も消します。

CLIではこのディレクトリで実行します。Python標準ライブラリだけを使います。

```sh
python3 -B model.py --policy shortest --view input
python3 -B model.py --policy shortest --predict-all-on-time yes
python3 -B model.py --policy deadline --predict-all-on-time yes
python3 -B model.py --order ABC --json
python3 -B verify.py
node check-reader.cjs
```

通常の検査は保存した記録を更新しません。`verify.py --record` は既存の実行記録があれば上書きを拒否します。

## 3. 原典と実装を確認する

[Google SRE「Latency and Deadlines」](https://sre.google/sre-book/addressing-cascading-failures/#xref_cascading-failure_latency-and-deadlines)は、要求が返答を待てる期限と、期限後も処理を続ける意味を考える一次資料です。本教材の数値、等値規約、順序比較は独自の有限条件であり、原典の測定結果ではありません。[出典と読取範囲](sources.json)に区別を残しています。

[手計算表](hand-oracle.json)と[固定時点の記録](hand-oracle-lock.json)を模型より先に保存しました。各順序の7個の時間区間を、たとえば `CBBAAAA` と手で記しています。[模型](model.py)は処理時間を累積して開始・完了を求めます。[検査](verify.py)は手書き列で初めて現れた位置・最後の位置・待つ区間の数を数え、累積処理を再利用せず照合します。

画面は検証済みの保存結果を読みます。模型の式をJavaScriptへ写して、それだけを一致の根拠にする方式ではありません。画面状態の検査でも手書き列から48時点を照合します。

## 4. 答え合わせ

待ち時間は開始時刻−到着時刻。全員が到着0なので今回は開始時刻と同じです。遅れは `完了−締切`、超過は `max(0, 遅れ)`。締切前に終われば遅れは負ですが、超過は0です。

|順序|完了 A / B / C|平均待ち|平均完了|期限違反|締切ちょうど|
|---|---|---:|---:|---|---|
|ABC：FIFO|4 / 6 / 7|10/3|17/3|Bが3超過|C|
|ACB|4 / 7 / 5|3|16/3|Bが4超過|なし|
|BAC：締切順|6 / 2 / 7|8/3|5|なし|A、C|
|BCA|7 / 2 / 3|5/3|4|Aが1超過|なし|
|CAB|5 / 7 / 1|2|13/3|Bが4超過|なし|
|CBA：短い順|7 / 3 / 1|4/3|11/3|Aが1超過|B|

固定6順序の中ではCBAが平均待ち最小ですが、Aは締切6に対して7で完了します。BACの平均待ちは8/3で大きくても、全員の締切を守れます。どの順序も仕事量は7、完了数は3、最後の完了時刻は7です。

平均最小と全期限達成を、この例では同時に満たせません。「締切が早い順ならどんな状況でも最適」という結論には広げません。

## 5. 検証結果と限界

[保存した計算結果](observations/model-check.json)は6順序・48状態・入力18件、入力拒否16件、誤った計算結果の検出6件、CLI5件の成功を記録しています。模型の確認は0.002315秒でした。これは検査処理の所要時間で、仕事の待ち時間やCPU性能ではありません。

最初の記録準備は文字列のUTF-8読取りで失敗し、続く確認は出典ファイルのhash収集段階で停止しました。[失敗記録](observations/attempt-01-failure.json)と当時のPythonファイルを保持し、成功した保存結果は2回目・再試行1回として記録しています。

画面の確認は25項目、59回の実クリック、8組のキー操作で通過しました。予想変更・順序変更・リセットで古い結果が消えることと、未選択の案内・誤予想への応答も確認しています。検証状況と制限は [GUI-QA.md](GUI-QA.md)、別担当の確認結果は [独立受入記録](../acceptance/capacity-deadline-tradeoff/acceptance.json) を参照してください。今回の画面確認では保存した計算結果を再生成していません。全体台帳は変更していません。[既存との違い](SCOPE-REVIEW.md)を確認できます。
