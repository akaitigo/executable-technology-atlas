tick 0にA–Eの5job、service2tick。同じ入力でserver数とpolicyを比べます。tickは秒ではなく、実serverの性能測定ではありません。

前提と読む順番

arrival/start/finish、FIFO、平均の分母が前提です。

  1. 元Subject：有限窓と未完了jobで分母を確認。関連するmultiwindow alertの窓と分母も比較。
  2. 先固定の定義・手書きtimelineから予想。
  3. 1台→2台→drop→backpressure→入力拒否の順に操作。
  4. 再現手順・実務判断と未教材の次実験を読む。

同時刻は完了（server番号順）→既存queue FIFOを開始→producer FIFOを受理。空serverで即開始、なければqueueへ。capacityは待機だけで稼働中jobを含みません。IDは識別子で優先順位ではなく入力順A–Eを守ります。

Google SRE Handling OverloadのPitfalls of QPS / Client-Side Throttlingで要求cost・受理・拒否の区別を確認。今回のbackpressureはadaptive throttlingの実装ではありません。


event-driven実装・独立unit-tick検査・実行と原票保存を比較。1台finishは2/4/6/8/10、2台は2/2/4/4/6。容量1dropはA/B/C受理、D/E drop。受理cohort3jobの平均だけでは全要求5jobを説明できません。


backpressureではD/Eがproducerで各2tick待ちます。queue平均4/5に加えproducer平均4/5があり、admitted→finish平均14/5に対しoffered→finish平均18/5。待ちは消えず観測境界の外へ移ります。実務では受理率・全要求cohort・時間の起点をそろえます。
