# Atlas：性能・容量工学：短い仕事を先にすると、誰が待つ？

平均の改善と、個々の仕事の改善を分けて判断するための独立教材です。長さが異なる3仕事を並べ替え、待ち時間と完了時刻を比較します。既存Portalにはまだ統合していません。全分野・分野全体の完了を示すものではありません。

既存計画の `learning/continuations/performance-capacity-engineering/two-server-bounded-queue/COVERAGE.md` 第1行「job cost が異なるとどうなるか」に対応します。順序の効果を切り分けるため、今回は**単一サーバー**に限定しています。既存の2サーバー・待ち行列上限の実験を、そのまま拡張したものではありません。

## 要求と仕組み

平均完了時間を短くしたいとき、誰かの完了が遅くならないかも確認します。

- 固定の仕事は A=5、B=1、C=1 tick。すべて到着時刻は0。
- 1台で1仕事ずつ実行し、実行を途中で中断しません。切替コストは0。
- FIFOの同時到着は登録順 A→B→C。短い順は B→C→A。同じ長さのBとCは登録順を保ちます。
- `start=直前のfinish`、`finish=start+service`。到着0なので、待ち時間はstart、応答時間はfinishです。
- tickは架空のモデル時間です。実行するPythonの処理時間を、仕事の待ち時間やサーバー性能として扱いません。

## 予想 → 操作

「短い順にすると、Aの完了時刻は早くなる・変わらない・遅くなる」のどれかを予想してください。

1. [index.html](index.html) をブラウザで開きます。macOSでは、このディレクトリで `open index.html` でも開けます。外部依存、HTTPサーバー、インストールは不要です。
2. 選択メニューか「前の順序」「次の順序」で比較する順序を選び、予想を入力します。端では進めない方向のボタンが無効になります。
3. スライダーか「1 tick進める」で、FIFOと選んだ順序を同じ時刻で比べます。時刻1・2・5・7の待ち／実行中／完了を確認します。
4. 平均だけでなく、A・B・Cそれぞれの完了と最後の完了時刻を確認します。
5. 原典と実装を読み、「予想と答えを照合する」を押します。順序を変えると予想・答え・時刻は初期化されます。

CLIでも同じ計算を実行できます。

```sh
python3 -B model.py --order ABC
python3 -B model.py --order BCA
python3 -B checker.py
```

Python 3 と Node.js がすでにある環境向けです。最後の検査は保存した計算結果・手計算・Python・JavaScriptを照合し、ファイルを更新しません。後日のUI・文書修正後のhashとHTMLリンクは [現行manifest](observations/current-source-manifest.json) へ、初回の数値実行hashは初回の実行ログへ分けて照合します。`--record` は、この独立教材の実行記録を明示的に更新するときだけ使用します。導入や権限変更は行いません。

## 正常な比較と、誤った判断の反例

手計算は実装前に [hand-oracle.json](hand-oracle.json) に保存しました。[保存時点の記録](hand-oracle-lock.json) は、その時点で実装ファイルが未作成だったことと手計算表のハッシュを記録しています。

|順序|Aの完了|Bの完了|Cの完了|完了の合計|平均完了時間|平均待ち時間|最後の完了|
|---|---:|---:|---:|---:|---:|---:|---:|
|A→B→C（FIFO）|5|6|7|18|6|11/3|7|
|A→C→B|5|7|6|18|6|11/3|7|
|B→A→C|6|1|7|14|14/3|7/3|7|
|B→C→A（短い順）|7|1|2|10|10/3|1|7|
|C→A→B|6|7|1|14|14/3|7/3|7|
|C→B→A|7|2|1|10|10/3|1|7|

正常な比較は、同じ3仕事・同じ処理時間で順序だけを変えることです。「平均完了が6から10/3に減ったので、全員が早く終わる」は誤りです。Aは5から7へ遅れます。さらに、最後の完了は7、完了数÷全体の時間は3/7のままです。順序変更で処理能力が増えたとは判断できません。

空文字、重複仕事、未知仕事、型の違う入力は拒否します。検査では期待した入力拒否を正常な教材結果と分けて記録します。また、Aの完了・平均・全体終了時刻を改変した計算結果3件が手計算照合で検出されることを確認します。実際のサーバー障害を起こした実験ではありません。

## 原典 → 実装 → 答え

[Google SRE「Handling Overload」の “The Pitfalls of Queries per Second”](https://sre.google/sre-book/handling-overload/#the-pitfalls-of-queries-per-second) は、リクエストごとに必要な資源量が違うため、件数だけでは負荷を捉えきれないと説明しています。本教材の5・1・1という処理時間はその問いを扱うための架空入力であり、原典の測定値ではありません。

[model.py](model.py) は処理時間を累積し、[app.js](app.js) は同じモデルと表示用の状態を計算します。[checker.py](checker.py) は実装前の手計算表に照合します。[check-js.cjs](check-js.cjs) は表示に使う純粋計算について、6順序×8時刻の48状態、入力拒否、予想と答えのリセットを確認します。

答えは、FIFOの平均完了が `(5+6+7)/3=6`、短い順が `(1+2+7)/3=10/3`。A自身は2 tick遅くなります。この固定6順序では、BCAとCBAが最小の平均完了時間です。一般の到着、期限、重み、推定誤差についての最適性を、この全列挙だけで主張することはできません。
