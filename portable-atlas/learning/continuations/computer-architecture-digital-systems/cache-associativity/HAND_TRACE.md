# Atlas：実装前に手で追う配置

容量16B、line4Bなので合計4行です。directのsetはblockを4で割った余り、2-wayのsetは2で割った余りです。どちらもcold start。以下は実測ではなく、模型を作る前の[固定手表](expected.json)です。

| trace | direct hit/miss/eviction/fetch B | 2-way LRU | 学ぶ差 |
|---|---|---|---|
| 0,16,0,16 | 0 / 4 / 3 / 16 | 2 / 2 / 0 / 8 | 同じsetでも2つのwayに保持できる |
| 0,8,16,0,8 | 1 / 4 / 2 / 16 | 0 / 5 / 3 / 20 | 同容量でset数が減り、3blockが同setで競合する |
| 0,8,0,16,0,8 | 2 / 4 / 2 / 16 | 2 / 4 / 2 / 16 | 集計が同じでも各時点のhit/victimは異なる |
| 3,0,4,7,255,252 | 3 / 3 / 0 / 12 | 3 / 3 / 0 / 12 | byteとblock、offsetを区別する |
| 空列 | 0 / 0 / 0 / 0 | 0 / 0 / 0 / 0 | hit率は0ではなく未定義null |

## hitの後を追う

`0,8,0,16,0,8`の2-way set0だけを見ると、block0とblock2をway0/1へ入れた後のLRU→MRUは`[0,1]`。3回目のaddress0はway0のhitなので`[1,0]`へ変わります。次のaddress16（block4）で追い出すのはway1のblock2です。way番号は固定位置なので、way0が常に古いわけではありません。

hit更新を省く故障では、3回目も`[0,1]`のままです。そのため4回目はblock0を追い出し、5回目のaddress0がmissになります。故障の集計は1 hit / 5 miss / 3 eviction / 20B取得。valid/tagとfillは壊していないので、返却byte列は正常と同じ`[3,139,3,19,3,139]`です。byte一致だけではLRU規則の正しさを確認できません。

## 同じ容量なのに2-wayが不利な例

`0,8,16,0,8`ではblock0/2/4が2-wayのset0へ集まります。最後のblock2は既に置換されmiss。一方、directではblock2がset2に残って最後がhitです。これは選んだtraceの結果であり、2-wayが一般に劣るという結論でもありません。

## byteの境界

`3,0`は同じblock0、`4,7`はblock1、`255,252`はblock63です。それぞれoffsetだけが変わり、最初のmissで4Bを取り込みます。返却列は`[54,3,71,122,242,191]`。取得量は要求1B×6ではなくmiss3×4B=12Bです。全解のような探索はなく、traceの順でreadする模型です。
