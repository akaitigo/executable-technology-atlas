03 · RECOVERY DECISIONS
失敗後、どのplanを承認するか
  1. exitと失敗stepを確認し、成功済みの副作用を分ける。サービスは依存resource不足で不完全かもしれない。
  2. failure traceとpartial stateを保存する。初期化して成功扱いせず、rollback済みと報告するには実証拠を求める。
  3. 実stateを再観測し、新planをレビューする。古いcreateの再実行は重複や副作用を起こす場合がある。
  4. 未適用分をreconcileしてno-opを再確認する。resource数の一致だけではreadinessや業務正常を保証しない。
実Terraform/provider/cloud、rollback保証、分散transactionは未実行。単一writer・create-only・順序固定・3resourceの合成storeです。lost updateやsnapshotの再検査はこの単元で重複実装しません。
