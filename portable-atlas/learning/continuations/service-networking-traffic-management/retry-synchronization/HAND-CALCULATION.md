# 先に固定した手追跡

全員の初回は `[0,1)`。ID順のAだけが受理され、t1にAの成功とB/C/Dの過負荷を観測します。ここまでの4call・効果1は全条件で同じです。以下の区間は実時間ではなく固定virtual tickです。

|条件|追加attemptの開始|成功の完了時刻 A/B/C/D|終了の相違|
|---|---|---|---|
|同期|t2:B,C,D → t4:C,D|1 / 3 / 5 / なし|Dは3回失敗、t5に追加retry枯渇|
|分散|t2:B → t3:C → t4:D|1 / 3 / 4 / 5|全員成功|
|偏り|t2:B,C,D → t4:C → t6:D|1 / 3 / 5 / 7|全員成功するが追加衝突と待機が残る|
|同期・予算5|t2:Bのみ。C,Dは予算拒否|1 / 3 / なし / なし|t2にC,DがCALL_BUDGET。追加retry残数は両者2のまま|

各開始区間の終了はstart+1です。予算内で同tick最初の1件だけを受理します。失敗の完了を見てから次delayを足すので、同期の次開始は0→2→4、0→1→2ではありません。

|条件|全call|追加retry|成功/不成功|合成効果|重複効果|retry同時開始の最大|全attempt同時開始の最大|
|---|---:|---:|---|---:|---:|---:|---:|
|同期|9|5|3 / 1|3|0|3|4|
|分散|7|3|4 / 0|4|0|1|4|
|偏り|9|5|4 / 0|4|0|3|4|
|同期・予算5|5|1|2 / 2|2|0|1|4|

分散のt3ではBが先に完了し、次にCが開始します。完了Bの効果2件目はこの時点で数えます。Cはまだ成功未観測です。偏りのDはt5では待機中、t6では実行中、t7で成功します。全条件のt7では未終端clientが0ですが、同期と予算5には成功していないclientが残ります。

[固定手表](hand-oracle.json)は全32tickの候補/開始/受理/予算拒否・累積値、30attemptの区間、16clientの終端をliteralとして保存します。全128client時点の状態は、この区間が選択tickを含むか、成功/最終失敗が完了したか、拒否時刻に達したかから別方式で求められます。producerの状態更新手順を再利用する必要はありません。

重複効果0は応答欠落を含めていない結果です。既存の[応答不明と再開判断](../agent-resume-uncertainty/README.md)へ戻ると、完了を知らず再送する場合の別の問題を確認できます。
