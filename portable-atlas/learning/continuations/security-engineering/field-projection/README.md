# Atlas｜読めるレコードでも、全項目を返してよい？

レコード単位の読取許可と、応答で開示する項目の許可を分ける教材です。上流の認証を仮定した小さなPython関数で、全項目を返す対照と、明示許可一覧から応答を作る修正版を比較しました。架空の3役割・3レコード・6項目を使います。

このディレクトリで `python3 -B serve.py` を実行し、[http://127.0.0.1:18758/](http://127.0.0.1:18758/) を開きます。入口は [index.html](index.html) です。画面は保存結果を選んで読むもので、実APIへの要求や認証を実行しません。

## 予想から答えまで

1. viewer / red-report を選び、修正版が何を返すか予想します。上流contextと利用者の要求を別々に読みます。
2. 「保存した比較結果を表示」で、objectのみの対照と修正版の実応答を比べます。対照は6項目、修正版はid・title・statusの3項目です。単に画面で隠しているのではなく、保存された修正版のpayloadにありません。
3. viewer / internal_noteだけ要求へ進みます。object自体は読めても、修正版は403でpayload=nullです。idとinternal_noteの混在要求も部分返却せず拒否します。
4. operatorとauditorを比べます。前者は連絡先、後者は内部メモを読めます。この業務ルールに上下関係はありません。
5. 将来項目を追加した条件では、対照が7項目へ増え、修正版は3項目のままです。storeの変更だけで開示範囲を広げません。
6. [原典の参照箇所](SOURCES.md)と画面内の実行時コードを読み、答えを照合します。拒否時の入力や検査順の説明を、応答payloadと取り違えないでください。

条件を変えると予想も消えます。予想だけを変えた場合は新しい選択を残し、古い結果と答えを消します。resetは同じ条件で予想からやり直します。読込失敗や内容不一致を、以前の成功表示で補いません。

## 前提と実務判断

目標73のfield開示に対応します。既存の [object認可](related.html?topic=object) は、object・operation・tenant・grantの検査を扱います。[確認と使用の間の変更](related.html?topic=toctou) は権限確認後の状態変化を扱います。画面末尾から固定した既存2資料の本文へ進めます。既存ファイルは変更していません。

ここでは両版ともobject検査を保ち、返す項目だけを変えます。匿名化や再識別リスクの評価、DBクエリの通信量・効率を目的とする射影は別の問題です。作者は教材数を加算せず、全体の重複判断は別途行います。

## 仮定と残る範囲

`context` は上流で正しく認証されたものと仮定します。requestへroleを追加すると400で拒否しますが、これはJWT・token・session検証の代わりではありません。不明roleの401や他のHTTP風の番号は、この関数模型の拒否規約です。実HTTPサーバーの安全性やエラー設計を実証していません。

実認証、policy/DB変更との競合、分散した強制、write側のmass assignment、存在情報・timing、一般のschema移行、実製品の安全認証は残ります。次の不足は [COVERAGE.md](COVERAGE.md)、再現は [REPRODUCE.md](REPRODUCE.md)、案内は [SKILL.md](SKILL.md) を参照してください。
