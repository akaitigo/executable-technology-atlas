# Atlas｜拒否したのに、値が変わっている？

書き込める項目の許可と、拒否した要求でstoreを変えないことを分けて確かめる教材です。3方式に同じ架空要求を与え、応答とstore全体の更新前後を別々に保存しました。

このディレクトリで `python3 -B serve.py` を実行し、[http://127.0.0.1:18760/](http://127.0.0.1:18760/) を開きます。入口は [index.html](index.html)。画面は保存結果を読むもので、利用者操作で更新handlerや実APIを再実行しません。

## 予想してから、変更を確かめる

1. [object認可](related.html?topic=object)と前の[読取field開示](related.html?topic=read-field)を読みます。read grantをwrite grantに読み替えないことを確認します。
2. operatorのtitle更新で、修正版の許可/拒否と、途中で検査する対照のstoreが変わるかを別々に予想します。
3. 「許可title → 禁止内部メモ」を選び、3方式を比較します。一括代入は2項目を変えて200、途中検査はtitleだけ変えて403、全検査後の修正版は403でstore不変です。
4. 「禁止内部メモ → 許可title」へ変えます。途中検査も最初に拒否するため、storeは変わりません。拒否番号だけを見ると同じでも、前の要求では部分更新が残っていました。
5. 各カードの応答と、診断用のstore差分を分けて読みます。詳細では対象外の2レコードも含むstore全体と検査順を確認できます。
6. [原典と実装](SOURCES.md)を読み、答えを照合します。全項目の検査を完了する前に、共有状態を変えてよいかを考えます。

条件変更は両方の予想を消します。予想変更は選択を保ち、古い比較と答えを消します。resetは同じ条件で予想からやり直します。取得失敗や内容不一致を古い成功表示で補いません。

## 24要求で観測したこと

| 方式 | 許可 / 拒否 | 拒否したのにstoreが変わった条件 |
| --- | --- | --- |
| 一括代入 | 11 / 13 | なし。ただし禁止項目も許可して変更する欠陥がある |
| 検査しながら更新 | 4 / 20 | 許可title→禁止内部メモの1条件 |
| 全検査後に反映 | 4 / 20 | なし。全拒否20条件でstore不変 |

修正版の正常4条件では、対象recordの指定した許可fieldだけを変更しました。他field・他recordは不変です。viewerのread grant、同tenantだけの一致、requestへ追加したrole/tenantではwriteを許可しません。役割表は教材固有で、operatorとauditorに上下関係はありません。

[保存した実行結果](observations/run-01/results.json)には24要求×3方式の72応答を保存しました。作者の固定手表との401確認、別担当の実装読取前の期待との555関係が一致しています。作者は5改変、独立担当は6改変を拒否しました。これらの確認には重複があり、網羅率として合算しません。

各要求・方式には独立した初期storeを与えています。要求単位のbeforeStoreと、方式ごとのafterStoreを保存しました。方式ごとの独立初期化は実行コードのcopy構造も併せて確認し、別々のbefore snapshotを保存したとは呼びません。入力不変は実行時の前後比較とコード読取の範囲です。

保存結果を読む画面では14項目・230回の実ポインター操作を確認しました。24要求の72応答、store差分、診断用の全before/after store、要求の挿入順、2つの予想の答えを実DOMへ保存しています。幅1280pxと390pxの実画像9枚を作者が目視しました。条件・予想・reset、取得失敗・改変・古い応答で以前の答えを残さないことも確認しています。

## 使える範囲

これは単一メモリ内のPython関数です。上流context・policy・初期storeを信頼する仮定で、実認証/JWT/HTTP/DBはありません。拒否番号は関数模型の規約です。修正版の候補recordの置換を、DB transaction、同時更新の原子性、プロセス停止後の回復へ一般化しません。

値は1〜80文字の文字列という制約を実装していますが、長さ0/1/80/81の端点は今回の24要求で個別実測していません。型不正は整数の1条件です。JSON重複キー、nested値、全ての値境界、連続サービスでの回復は別の不足です。

初期契約の見出しは実行当時のまま保持し、画面では「変更が残る」問いに明確化しました。[文言の修正記録](document-revisions/pre-gui-wording/verification.json)は計算の再実行や期待表の変更ではありません。旧教材・元repo・共有台帳は変更せず、作者の加算は0です。
