03原典と実装に戻る

固定commitの sync_context.go を読み、この3つの境界を教材へ取り込みました。

  1. prune wave の両端を交換：−3、1、8 → 8、1、−3。符号反転ではありません。
  2. 削除待ちで戻る条件：Pruned、liveあり、deletionTimestampあり。
  3. 現在wave内でpruneを先に処理：SyncFailedならapply側へ進まず戻ります。
教材の実装・原票を確認する

04予想と答えを比べる

対照を最後まで進めると答えを開けます。予想を変えると、段階と答えも最初に戻ります。

05実務で判断する、その前に

Pruned と「資源が消えた」は別です。 元wave・有効wave、結果、liveの有無、deletionTimestampを分けて確認します。SyncFailedの原因は実際のcontroller/APIの記録を調べてください。

この教材はSync phase、ConfigMap、prune有効、PruneLast無効、確認条件充足、hookなし。初期タスク集合を固定し、結果とlive観測は仮定入力です。最終wave後の消滅やHealth、再計画、一般の依存解消、cycle解決を保証しません。
