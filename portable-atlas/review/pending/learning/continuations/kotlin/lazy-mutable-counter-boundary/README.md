# Atlas：lazy の安全な初期化は、その後の更新も守るか

同じカウンターを2人が1回ずつ増やすと、最終値は必ず2になるでしょうか。この教材ではSYNCHRONIZED lazyによる初期化を共通にして、取得後の4種類の更新を比べます。

[学習画面](index.html) → [前提・原典・コードへの案内](reference.html) → [限定Skill](SKILL.md) の順で使います。[測定結果と初回失敗の記録](MEASUREMENTS.md)、[実画面で確認した範囲](GUI_VERIFICATION.md)も読めます。実行と画面確認の現在状態は [状態記録](status.json) を参照してください。保存結果の閲覧にcompilerの再実行は不要です。

到達目標は、初期化と公開後の操作を分ける、同じ参照を確かめる、read+writeの分割で失われる更新を説明する、atomicなget/setと複合atomic操作を分ける、適切なlock範囲を選ぶ、有限同期が作る順序と保証外を説明する、の6点です。

1. 4条件の最終値と理由を予想します。
2. getter前、初期化時、workerごとの記録、終了後の順に保存結果を読みます。
3. 合法の正常終了でも更新が1つ失われる対照と、2が残る修正を比較します。
4. [原典](SOURCES.md)と[実装](src/LazyMutableCounter.kt)を読み、最後に答えを開きます。

## Atlas の大事な区別

plain-split/atomic-splitは「両者が0を読む→Barrierで待つ→各自1を書く」を作ります。偶然の競合を何回も試す実験ではありません。Barrierが加える可視性と順序があるため、メモリ可視性一般の不具合とは呼びません。lock版はlockに入る前で待ち、readとwriteを同じ区間に入れます。Lazy自身とは別のlockです。

incrementAndGetは返された値だけを記録します。更新前の別getを観測したとは主張しません。worker A/Bの回収順はCPU全体の実行順ではありません。初期化前はpayloadが存在しないため、その値は未観測です。constructorが設定した0は初期化時の記録として読みます。

## Atlas のローカル利用と再現

このディレクトリを作業場所に、既存Pythonで `python3 -m http.server 8765 --bind 127.0.0.1` を手動で起動し、`http://127.0.0.1:8765/` を開けます。使用中のportは避けてください。画面の資料HTMLは本文表示、MarkdownやKotlinファイルは配信環境によってダウンロードになります。ダウンロードされた内容を画面本文とは扱いません。

新たに計算する場合は [実行条件](RUN_CONDITIONS.md) の資源・root管理枠・今回identity判断・実nice・時間制限を確認し、新しい保存先へ1回だけ進みます。過去のPID許可を流用しません。保存済みの数値を読むだけなら実行は不要です。

対象は固定JVMの2実threadであり、複数CPU coreでの同時実行や、あらゆる並行操作の安全性を証明しません。[未対応の範囲](COVERAGE.md)を確認してください。
